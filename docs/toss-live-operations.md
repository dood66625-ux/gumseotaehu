# 토스 실운영 승인·조회·전액 환불·구매 증빙 연결

2026-11-19 KST. **코드 연결 완료이며 실제 운영 활성화·카드사 심사 완료가 아니다.** 이번 작업은 가짜 키·모의 HTTP로 검증했다. 실제 결제/조회/취소/운영 키 입력/서버 전환은 수행하지 않았다.

## 운영 경로

기존 `TossTestContract`와 테스트 HTTP는 운영 키를 계속 거부한다. 별도 `TossLiveContract`와 live HTTP는 test 키를 거부하고 고정 `https://api.tosspayments.com` 승인/조회와 아래 별도 승인된 전액 취소 경로만 허용한다. 리다이렉트·임의 host·자동 HTTP 재시도는 없다. 10초 요청 제한과 256KiB 응답 제한을 유지한다. 기본 운영 transport는 취소 POST를 거부하며, 명시된 운영 환불 경로에서만 취소 capability를 부여한다.

서버의 `payments/confirm` 경로는 `TOSS_PAYMENT_MODE=live`일 때만 live coordinator로 분기한다. 기존 세션·주문 소유권·동일 origin POST 검사를 그대로 거친다. 운영 모드 또는 모드 오타는 모의 승인으로 대체하지 않는다. `payments/authenticate`의 모의 결제도 서비스 함수에서 차단한다. 운영으로 바인딩된 주문은 모드를 disabled로 돌려도 모의 승인/환불로 우회하지 않는다.

명시한 실운영 승인과 HTTPS, 운영 key/mId, 서명된 전환 파일, 같은 DB의 등록과 source ID가 모두 필요하다. 전환 파일은 origin·mId·키 fingerprint에 묶이며 private 0700 디렉터리의 0600 일반 파일이다. 파일에 키 원문은 없다. 예전 파일 덮어쓰기·다른 키/DB/상점·미래 시각·변조는 거부한다. 실제 상점 키 조합의 유효성은 형식 검사만으로 검증됐다고 표시하지 않는다.

운영 최초 등록은 기존 Toss 테스트 시도가 있는 DB에서는 거절한다. 테스트 sandbox DB/운영 DB를 분리하고 전환 시각 이후 생성한 신규 주문만 승인 대상으로 삼는다. 첫 승인 전에 주문을 별도 `toss_live_orders`와 AI 작업 경로에 원자적으로 묶어 운영 구매에 모의 운명서가 생성되는 것을 막는다. 실제 AI 환경/예산 승인은 별도이므로 준비되지 않으면 운명서는 자동 생성되지 않는다.

실제 HTTP 응답은 paymentKey·orderId·서버 금액·mId·KRW·NORMAL을 모두 대조하고 기존 coordinator가 승인 시각/잔액/취소 증거까지 검증한다. 최초 승인 시도와 paymentKey를 DB에 먼저 저장한다. 응답 유실/중단 뒤에는 같은 결제키로 GET만 수행하고 confirm POST를 다시 보내지 않는다. 중복 성공 callback은 기존 확인 상태를 반환한다. 결제키가 다른 callback·다른 주문에 붙인 결제·금액 불일치는 거부한다.

일반 worker의 복구는 이번 운영 profile에 연결된 주문만 최대 5건씩 조회한다. 과거 테스트 시도/다른 상점/다른 profile은 조회하지 않는다. 주문별 기존 lease·대기/백오프·독립 조회·반복 알림 보존 정책을 유지하고 종료 신호가 오면 다음 조회를 시작하지 않는다. 운영 승인/조회 감사 기록은 `toss-live`로 구분한다.

## 서명 웹훅

`/api/toss/webhook`의 운영 분기는 `TOSS_LIVE_WEBHOOK_MODE=signed-live-only`와 별도 운영 security key를 요구한다. 기존 원문 bytes와 transmission-time HMAC·전송 시각 허용 범위·중복 제거 검사를 재사용한다. **해당 운영 계정에서 이 서명 형식을 제공하는지 토스 설정에서 먼저 확인해야 하며**, unsigned callback을 허용하는 우회 옵션은 없다. 지원되지 않거나 미등록이면 운영 웹훅은 비활성으로 남긴다.

수신은 공급자 HTTP 요청을 하지 않는다. 등록된 운영 주문·paymentKey·mId가 일치하는 알림만 독립 조회 대기로 기록한다. 서명된 본문이 DONE/CANCELED라고 해도 그 주장으로 결제/환불을 변경하지 않는다. 본문 조작·다른 상점·오래된 전송·다른 주문 연결은 기존 검증으로 차단한다. 실제 등록/외부 전달/재전송/시계 동기화 실증은 아직 남았다.

## 승인된 전환 때 필요한 설정

| 설정                                                       | 용도                                                                                          |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `TOSS_PAYMENT_MODE=live`                                   | 운영 전용 경로 선택. 기본 미설정/disabled는 모의 체험이다.                                    |
| `LIVE_PAYMENTS_APPROVAL=live-payments-approved`            | 별도 실결제 운영 승인 표시. 키 존재만으로 활성화하지 않는다.                                  |
| `TOSS_LIVE_SECRET_KEY`, `TOSS_LIVE_MERCHANT_ID`            | 운영 상점 키와 MID. 일반/위젯 계열을 구분하며 test 키는 거부한다.                             |
| `TOSS_LIVE_CUTOVER_FILE`                                   | 영구 private 서명 전환 파일 경로. 승인된 비공개 데이터 디렉터리/같은 권위 DB와 별도 보관한다. |
| `APP_ORIGIN` / `DATABASE_PATH` / `DATA_KEY`                | 동일한 운영 origin·SQLite·암호화 키. HTTPS 필수.                                              |
| `TOSS_LIVE_WEBHOOK_MODE`, `TOSS_LIVE_WEBHOOK_SECURITY_KEY` | 토스가 제공하는 운영 서명 webhook 등록/검증용. 고객 화면에 전달하지 않는다.                   |

판매·모든 worker를 정지한 상태에서 운영 승인을 받은 관리자가 기존 체크포인트 source ID와 분리된 DB/키/MID를 확인한 뒤 `npm run toss:live:enroll -- --enroll --approve-live-payments`를 사용한다. 패키지에서는 `node dist/toss-live-enroll.js --enroll --approve-live-payments`다. 이 명령은 등록/파일만 생성하고 결제 API를 호출하지 않는다. 재등록을 거부하며 파일 생성 후 DB 커밋 실패 시 파일을 자동 삭제/덮어쓰지 않는다.

이번 작업에서는 위 명령이나 설정을 서버에 적용하지 않았다. 운영 client key/카드창과 실제 callback 연결, 통제된 운영 승인·외부 webhook 수신, AI/메일/환불/PDF 접근 종료를 함께 확인하는 최종 인수는 남는다. 기존 심사용 테스트 카드창/테스트 키 설정은 운영 카드창으로 바꾸지 않았다. 테스트 카드창이 보인다는 사실만으로 실제 판매 가능하다고 표시하지 않는다.

## 복원·차단 대응

- 공식 암호화 복원 도구는 `toss_live_enrollment.recovery_hold=1`로 표시한다. 조회/승인과 모의 생성 선점도 멈추며 자동 재등록/보류 해제는 없다. 최신 공급자 거래·주문·비용/삭제 원장 대조 뒤 별도 운영 복구 검토가 필요하다. 원장 임의 삭제나 과거 DB 복사로 우회하지 않는다.
- `TOSS_LIVE_NOT_ENROLLED`: DB/전환 파일 경로와 실제 등록 유무를 확인한다. 복원 후 소실된 원장을 새 등록으로 덮지 않는다.
- `TOSS_LIVE_PROFILE_MISMATCH` / `TOSS_CUTOVER_MISMATCH`: origin·MID·키·DATA_KEY·파일/DB가 같은 운영 구성인지 대조한다. 키 회전은 별도 재전환 검토 대상이다.
- `TOSS_LIVE_ISOLATED_DATABASE_REQUIRED`: 테스트 결제 시도 DB를 운영으로 승격하지 않는다. 운영 DB 준비와 기존 기록 이전 범위를 별도 검토한다.
- 승인 응답 유실: 추가 결제를 요구하지 말고 같은 주문의 독립 조회를 사용한다. provider 원문/키/개인정보를 오류에 출력하지 않는다.

서명 파일/DB가 과거 시점으로 함께 복사되는 경우의 최신성, 운영 권한/실제 거래 증거, 실기기 카드창 복귀와 재전송, 외부 결제 취소 실증은 별도 남은 검증이다. 이 코드는 부분취소·가상계좌·복합결제를 운영 지원한다고 선언하지 않는다.

검증: 토스 HTTP/주문/서명 알림·전환/코어/AI/상태/패키지 336개 테스트와 타입·전체 빌드·비밀값 검사 통과. 운영 서명 HTTP route의 중복 수신도 추가 검증했다. 모든 공급자 요청은 주입한 가짜 fetch였고 실제 결제/조회/취소 요청은 0회다.

출시 진행표 3.1.5는 운영 백엔드 연결 완료다. 3.1.7 운영 카드창·복귀 화면 개발을 별도 항목으로 추가했으며 그 항목과 실제 운영 인수 전에는 일반 구매가 가능하다고 표시하지 않는다.

## 운영 위젯·결제 복귀 화면 연결 (2026-11-20 KST)

일반 Next 앱의 결제 화면은 인증된 `payments/config`에서 모드를 확인한다. 미설정/disabled만 기존 체험을 사용하며 설정 조회 실패/잘못된 운영 설정은 모의 승인으로 대체하지 않는다. 기본 체험·심사용 공개 정적 페이지는 운영 SDK를 요청하지 않는다.

운영 모드는 주문/동의를 먼저 저장한 뒤 `payments/prepare-live`에서 소유권·pending 상태·미삭제·전환 이후 생성·서명 등록을 확인한다. 응답은 공개 `TOSS_LIVE_CLIENT_KEY`, 서버 주문 금액/KRW·주문 ID/고정 상품명뿐이며 secret key는 반환하지 않는다. 현재 고객 화면은 **위젯용 live_gck/live_gsk 조합**만 지원한다. 일반 live_ck/live_sk 계열을 위젯으로 잘못 사용하면 거부한다. 형식/계열 검사는 실제 MID 소유/키 쌍 유효성을 증명하지 않는다.

고정 `https://js.tosspayments.com/v2/standard` SDK만 승인된 운영 화면에서 동적으로 불러온다. `ANONYMOUS` customerKey로 이름/이메일을 SDK에 추가하지 않고 저장된 서버 금액을 setAmount한다. 결제 수단 DEFAULT/약관 AGREEMENT 위젯을 렌더링하고 필수 약관 상태가 참이어야 requestPayment를 호출한다. SDK 로드/일부 렌더 실패 시 같은 주문으로 다시 준비할 수 있고, 완료된 창 열기 요청은 반복하지 않는다. 주문 화면별 DOM 대상과 읽기별 컴포넌트 key를 구분해 다른 출생정보로 이동한 화면에 이전 위젯을 연결하지 않는다.

successUrl은 같은 origin의 `/checkout/success`, failUrl은 같은 origin의 `/checkout/fail?orderId=<현재 주문>`으로 고정한다. 복귀 화면의 paymentKey/orderId/amount는 미신뢰 입력이다. 별도 `payments/live-return` 경로가 기존 운영 승인 coordinator를 호출하며 체험 승인으로 우회하지 않는다. 자동 호출은 한 번, 중복 클릭은 잠근다. 통신 실패/불명확한 응답은 자동 POST 재시도를 하지 않으며 같은 주문 재확인 버튼과 주문 조회를 제공한다. 승인 URL에 돌아온 사실만으로 운명서를 열지 않고 `PaymentStatus`가 조회한 서버 결제/제공 상태가 기준이다.

서버가 응답한 뒤에만 주소에서 paymentKey/amount를 제거한다. 응답 유실로 서버가 아직 기록하지 못했을 가능성이 있으면 주소/메모리의 복귀 정보를 유지하여 같은 주문을 수동 확인할 수 있다. 기존 no-referrer/no-store 정책을 유지한다. 취소·실패 화면은 제공자 오류 원문/입력값을 표시하지 않고 유효한 주문 ID의 상태 확인 또는 이메일 복구로 안내한다.

기존 ‘실제 결제 없음’ 배너/문구는 일반 앱의 신뢰한 운영 모드에서 표시하지 않는다. 정적 공개 심사 페이지는 기본 체험 표시를 유지한다. root layout은 runtime 모드가 과거 빌드의 체험 안내로 고정되지 않게 요청 시 렌더링한다. 메인의 정적 HTML route는 그대로 유지한다. CSP는 고정 SDK host와 토스 connect/frame host만 추가하며 임의 script host를 허용하지 않는다.

검증: 실제 React Checkout/PaymentReturn 컴포넌트와 모의 SDK/HTTP로 390px/1440px의 기본 SDK 요청0회·서버 금액·필수 약관·단일 창 열기·1회 복귀 확인·실패 후 자동 재시도 없음·수동 동일 주문 재확인·잘못된 복귀 값 미제출·서버 pending 상태의 열람 차단을 확인했다. `npm run test:live-checkout`로 재현한다. 서버/토스/코어291개와 기존 결제 상태 복구 모바일/PC E2E 2개, 타입·빌드·비밀값 검사도 검증한다. 모든 공급자 SDK/API는 가짜 응답으로 가로챘고 실제 결제/조회/취소 요청은 0회다.

실제 상점 DEFAULT 위젯에서 계약 범위에 맞는 카드 수단만 노출하도록 토스 UI 설정을 확인해야 한다. 실제 SDK/카드앱·브라우저 복귀/CSP·MID/위젯 키·기기 동작은 별도 운영 검증이다. 일반 앱 호스트/HTTPS·실제 키·상품/개인정보 승인·AI/메일 설정·운영 환불·심사·최종 인수 전에는 실제 판매를 켜지 않는다. 이번 작업에서는 서버 환경변수/키/상품/컨테이너를 변경하거나 유료 요청을 보내지 않았다.


## 운영 전액 환불·구매 증빙 연결 (2026-11-21)

개발 완료 조건3.2.3의 연결이며 실제 상점 활성화/환불 실증이 아니다. 기존 서명 전환 파일·등록 DB·profile/cutoff·운영 결제 승인에 더해 `LIVE_REFUNDS_APPROVAL=live-refunds-approved`가 있어야 취소/취소 재시도를 허용한다. 이번 작업은 이 설정이나 실제 키/서버 환경을 변경하지 않았다. 기본 transport/일반 승인·worker 조회는 취소 권한이 없다.

관리자 주문 목록은 DB에 바인딩된 운영 주문과 모의 주문을 구분한다. 운영 주문은 모드를 disabled로 바꿔도 모의 환불로 우회하지 않는다. `/api/admin/refund`는 최근10분 MFA·operations/finance·해당 profile 주문·서버 금액/결제키·검토 사유5~200자를 확인한다. 운영 주문에서 모의 실패 시험 플래그true는 거절한다. 취소/재시도 API는 명시적인 confirmLiveRefund=true를 요구하며 UI는 조회된 목록에서 실제 선택한 운영 주문에만 이를 붙인다. 목록에 없는 주문번호로 바꾸면 금융 실행을 막고 검색/선택을 안내한다. 환불 승인 설정이 없으면 원장/환불 상태 변경이나 외부 요청을 하지 않는다.

금액을 사용자가 보내지 않으며 전액만 지원한다. 원자적으로 환불 대기/한 번의 발송 의도를 기록하고, 취소 직전 독립 GET에서 주문·key·MID·KRW/NORMAL·금액·완납 잔액과 승인 상태를 대조한다. 이미 확인된 전액 취소라면 POST 없이 해당 증거로 정리한다. 부분취소/잔액 불일치/다른 결제는 취소 POST를 보내지 않는다. 취소 요청은 고정된 일반 사유와 서버 금액, `live-cancel-<orderId>` 멱등키를 사용하고 관리자가 적은 사유/개인정보는 공급자 본문으로 보내지 않는다.

응답 유실 후 자동 취소 POST 재전송은 없다. 기존 worker·관리자 `/api/admin/refund-check`는 GET만 수행한다. `/api/admin/refund-retry`는 최근 독립 조회에서 미취소DONE 확인·저장 환불 사유·14일 이내 원요청·lease/MFA/승인 조건을 다시 요구하며 같은 멱등키/금액/일반 사유로 명시 재시도한다. 관리자 화면도 처리 중·미확인·전액 취소 확인을 구분하고 재시도에 별도 확인 체크를 요구한다. 확인된 CANCELED/잔액0/단일DONE전액 취소 증거만 기존 원장 대조 후 refunded로 반영하며 대기 생성 작업 취소·웹/PDF 열람 종료를 적용한다. 로컬로 저장한 파일을 삭제하는 기능은 아니다.

구매 증빙은 주문 상태 화면에서 고객이 요청할 때만 `/api/orders/<id>/receipt`로 조회한다. 이메일 인증된 주문 소유권·현재 profile/cutoff·저장 결제키/원장·완료 결제 상태를 확인하고 토스 GET 응답의 동일 주문/MID/금액을 대조한다. 원문 결제키나 전체 응답은 반환하지 않는다. `https://dashboard.tosspayments.com/receipt/redirection`과 transactionId/ref만 허용하며 임의 host·인증정보·다른 경로·fragment·중복transactionId·임의 redirect 매개변수를 거부한다. 클라이언트도 같은 함수를 사용해 주소를 재검증하고 명시적 새 창 링크에 noopener/noreferrer/no-referrer를 적용한다. URL은 DB·감사 로그에 저장하지 않으며 응답은private no-store다. 다른 주문으로 이동한 뒤의 늦은 응답은 이전 컴포넌트에서 폐기한다. 공식 영수증 형식이 달라지면 안전하게 거절하며 실제 계약 경로 검증 후 허용 범위를 검토한다.

검증: 코어/토스 원장·운영 transport·영수증268개, 모바일/PC Chromium18개와 타입/전체 빌드 통과. 승인/MFA 누락 요청0, GET→단일 취소, 반복 취소 중복0, 응답 유실GET복구, 부분 잔액POST0/조회 뒤 명시 재시도, 타인 영수증 요청0/다른MID·악성URL차단, 관리자의 환불 대기/조회/재시도 분리와 고객 명시 조회/위험 링크 폐기를 검증했다. 모든PG 응답은 가짜 fetch/브라우저 가로채기이며 실제 승인/조회/취소/영수증 요청0회다. 실제 상점별 키·영수증 형식·동일 멱등키 취소 재시도·카드 앱/환불/PDF/메일 인수는3.2.4와 출시 인수에 남는다.
