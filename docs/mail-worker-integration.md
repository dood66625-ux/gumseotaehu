# 거래 메일 발송 사이클 후보

`lib/mail-worker.ts`는 큐 준비와 공급자 독립 전달 처리를 잇는 후보 구성이다. 일반 앱 worker에서 호출하지 않으며 실제 발송을 활성화하지 않는다. API 키 존재나 환경변수 하나만으로 등록되지 않는다.

`runMailCycle`은 기본 비활성이다. 명시적으로 활성화해 호출할 때도 `createdAtOrAfter` 기준 시각을 요구한다. 향후 운영 등록 시에는 승인된 전환 시각을 영구 보관해 동일하게 사용해야 하며, 프로세스 재시작마다 현재 시각으로 바꾸면 안 된다.

- 한 사이클은 최대 25개 준비, 한 건 전송/조회만 수행한다.
- 기준 시각 이전 메일은 준비뿐 아니라 이미 준비된 큐의 자동 처리에서도 제외한다.
- 복원 후 보류된 메일은 자동 처리하지 않는다. 별도 대조/검토가 필요하다.
- 실제 송신 직전 인증번호 만료·사용·재요청·입력 횟수 소진, 주문 환불/삭제와 수신 거부를 다시 검증한다.
- Resend 접수 성공은 accepted이며 delivered로 표시하지 않는다.
- 응답 유실로 공급자 ID를 저장하지 못한 경우 수락되지 않았다고 추측해 재전송하지 않는다.
- Sending access 키의 조회 거절은 전달 완료로 인정하지 않는다. 해당 제한을 없애려고 API 권한을 임의 확장하지 않는다.

검증: 관련 테스트 37개와 타입 검사 통과. 실제 HTTP 어댑터의 요청 구성·응답 파싱을 메일 큐 DB와 함께 실행하되 모든 외부 요청은 주입된 모의 fetch로 처리했다. 실제 고객 메일/Resend 네트워크 요청은 없었다.

남은 사항: 운영 worker 등록, 전환 시각 영구 저장, 계정 범위별 권한·전달/반송 증거 확보, 실제 인증 재열람, 운영 TLS와 로컬 OTP 조회 경로 제거, 승인된 개인정보 처리·외부 전송 조건 확인. 이 후보가 준비됐다고 고객 발송 가능으로 표시하지 않는다.

## 큐 운영 점검 도구 (2026-11-17)

`npm run mail:status -- <기존 SQLite 경로>`는 명시한 DB를 SQLite 읽기 전용으로 열고 한 스냅샷의 집계만 출력한다. 런타임 번들에서는 `node dist/mail-status.js <기존 SQLite 경로>`로 실행한다. 환경파일·복호화 키·메일 공급자 키가 필요 없으며 DB 생성/마이그레이션/큐 수정/발송/조회 API 호출을 수행하지 않는다. 공개 HTTP 경로나 자동 발송 worker에 등록하지 않았다.

- 상태별 건수, 복원 보류, 만료된 발송 lease, 15분 이상 처리되지 않은 발송 대기, 24시간 이상 전달 확인이 없는 접수를 구분한다.
- `review`, 불명확한 응답, 차단, 알 수 없는 상태도 경고한다. 알 수 없는 상태 원문은 `other` 건수로만 출력한다.
- 주소·해시·인증번호·본문·주문/공급자 ID·오류 원문은 출력하지 않는다.
- 종료 코드: 0=점검 성공/현재 정의된 경고 없음, 2=점검 성공/검토 필요, 1=DB 접근 또는 스키마 등 점검 실패. 코드 0은 발송 활성화·실수신 성공·출시 준비 완료를 뜻하지 않는다. 반송/신고 건수는 결과 이력이며 그 자체를 큐 정체로 계산하지 않는다.
- `MAIL_DELIVERY_UNCONFIRMED`는 재전송 지시가 아니다. 공급자 계정의 이력을 확인하고 기존 멱등/조회 정책에 따라 검토한다. 복원 보류도 이 명령으로 해제하지 않는다.

검증: 실제 스키마/SQLite와 CLI에서 개인정보 비노출, 상태별 경고, 활성 lease 제외, 복원 보류 구분, DB 바이트 보존 및 없는 DB 생성 방지를 검사했다. 관련 테스트 4개와 타입 검사 통과. 실제 고객 메일 발송과 서버 실행은 하지 않았다. 이메일 보강은 약 90%, 전체 출시 준비도 약 73%를 유지한다.

## 인증/재열람 화면 추가 검증 (2026-11-17)

구매 이메일 변경 시 대상 주소를 명시하고 15분/5회 안내, 주소 수정/재요청, 이전 체험 코드 표시 제거, 만료된 확인/코드 조회 차단, 비동기 중 중복 조작 방지를 추가했다. 서버의 기존 최근 구매 주소 인증·변경 요청 대체·만료/시도 횟수 제한은 유지한다. 화면에서 주소를 수정하는 것만으로 서버의 대기 요청이 취소됐다고 주장하지 않으며, 새 요청이 성공하면 기존 요청을 무효화한다.

모바일/PC Chromium 이메일 화면 E2E 4개와 실제 로컬 주문의 변경 후 동일 보고서 재열람/이전 주소 접근 차단 E2E 1개, 서버 변경 코어 5개를 검증했다. 공개용 정적 빌드에서는 새 기본값 처리에 맞춰 합성 이메일 고정 변환을 수정했고 읽기 전용/주소 수정 후 합성값 유지/백엔드 요청 없음도 브라우저로 확인했다. 빌드·타입·비밀값 검사를 수행했다. 실제 고객 발송/새로운 시험 메일 발송은 하지 않았다.

## 관리자 메일 점검 연결 (2026-11-18 KST)

기존 관리자 개요에 `mailHealth` 집계를 연결했다. 기존 관리자 역할 검사를 통과해야 조회할 수 있으며 공개 health/API나 심사용 결제 서버에 새 관리자 경로를 만들지 않는다. 기존 기본 건수와 별도로 결과 불명확/별도 검토/복원 보류/15분 이상 대기/첫 발송 시도 후 24시간 이상 전달 미확인과 검토 안내를 표시한다. 집계 시각을 표시하며 조회 당시 스냅샷이지 상시 알림 시스템은 아니다.

새 필드는 건수와 정해진 상태 코드만 반환한다. 주소·인증번호·본문·공급자 ID를 추가하지 않고 메일 큐를 수정하지 않는다. 새 발송/재발송/복원 보류 해제 버튼은 없다. 경고 없음도 실제 발송 활성화·실수신·출시 준비 완료가 아니라고 명시한다. 공급자 접수와 전달/고객 열람/PDF 저장을 구분한다.

검증: 관리자 사칭 역할 거절/집계 개인정보 비노출/큐 상태 보존 1개, 기존 집계·CLI 4개, 관리자 개요를 사용하는 비동기 보고서 생성 10개, 실제 모바일 구매/PDF/재인증/문의/관리자 점검 표시/mock 환불 E2E 1개, 타입·빌드·비밀값 검사 통과. 실제 메일 발송과 서버 운영 설정 변경은 없다. 이메일 약 90% / 출시 약 73% 유지.
