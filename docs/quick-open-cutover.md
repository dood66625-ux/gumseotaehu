# 퀵오픈 판매 전환

2026-11-26 KST. 소유자가 퀵오픈 가입 상태라고 확인했다. 카드사 심사 완료만을 기다리는 것을 오픈의 필수 선행 조건으로 두지 않는다. 실제 상점의 활성화·계약/정산 조건과 실제 결제 연동은 별도로 확인해야 한다.

토스 공식 안내: https://www.tosspayments.com/quick-open . 가입·결제 연동 후 심사 중 결제를 받을 수 있으며, 정산은 공식 안내상 심사 결과 통보일로부터 90일 뒤다. 거절 또는 신청 후 90일 내 미완료 시 제한될 수 있다. 가입 상점별 실제 안내와 대조한다.

## 현재 확인한 것

- 공개 `/start`와 `/api/auth/request`는 각각 HTTP404다. 현재 프록시는 심사용 정적 사이트와 제한된 관리자·방문 기록 API를 제공한다. 이를 실제 구매 흐름과 혼동하지 않는다.
- 이 작업 환경에서 `gumseo@115.68.223.204:22` 연결은 거부됐다. 서버 환경값·실제 키·실제 활성화 상태는 확인하지 못했다.
- 실결제/AI/메일 활성화, 외부 공급자 요청, 운영 DB 등록·전환은 실행하지 않았다.

## 바로 실행 가능한 읽기 전용 점검

최신 소스를 받아 서버에서 실행한다. 실행 중인 일반 web/worker를 각각 확인한다. 키/비밀번호/이메일/DB 경로는 출력하지 않고 상태만 표시한다. DB는 읽기 전용으로 열며 존재하지 않는 DB를 생성하지 않는다. 공급자 호출이나 설정 변경은 없다.

```bash
cd /opt/gumseo/source && git pull --ff-only && sudo bash deploy/iwinv/check-quick-open.sh
```

웹과 worker의 설정은 따로 본다. 실결제, 고객 AI, 고객 메일 설정과 각각의 전환 파일·등록 상태, 예산 설정을 확인한다. 이 점검의 `runtimeConfigurationComplete=true`만으로 판매 가능을 확정하지 않는다. 파일 서명/프로필 일치·실제 키 유효성·외부 공급자 계약 상태·종단간 동작은 별도로 검증한다. 출력에 `launchReady=false`를 유지하는 이유다.

## 준비된 전환 설정

`deploy/iwinv/Caddyfile.sales-candidate`는 검토용이며 현재 설치 스크립트에서 사용하지 않는다. 본 도메인을 실제 Next 앱으로 전달하고, 비밀파일·모의 OTP 조회·모의 승인 경로는 차단한다. pay.gumseo.kr의 기존 심사·비공개 reader 설정은 유지한다. 아래 조건을 확인하기 전 설치하지 않는다.

1. 실제 앱 origin을 HTTPS 도메인으로 맞추고 web/worker가 같은 운영 DB·암호화 키를 사용하는지 확인한다. 기존 테스트 결제 DB와 운영 원장을 섞지 않는다.
2. 기존 운영 위젯 gck/gsk 조합과 MID·서명 전환 등록·복원 보류 상태를 기존 런타임 검증 함수로 확인한다. 테스트 키를 운영 키로 오인하지 않는다.
3. 결제 후 AI 보고서 생성 경로·건별/일별/누적 예산·전송 동의와 메일 인증/재열람 경로가 준비돼 있어야 한다. 기존 가상 운명서를 유료 상품으로 제공하지 않는다.
4. 위 조건을 만족한 뒤 실제 고객 경로를 전환하고, 승인된 최소 범위의 실제 구매→저장 운명서→메일/PDF→취소/접근 종료를 인수한다. 통제된 검증에 필요한 실제 요청·금액·예산을 먼저 확정한다.

진행표는41/56(73.2%) 유지다. 퀵오픈 확인을 카드사 심사/정산 조건 전체 인수 완료로 부풀리지 않는다. 다음 필요한 증거는 위 서버 점검 출력이며 비밀값을 붙여 보내지 않는다.

### 전체 상태를 짧게 공유하기

긴 JSON의 마지막 메일 항목만 보이면 결제·AI 상태는 알 수 없다. `sudo bash deploy/iwinv/check-quick-open.sh --summary`는 컨테이너별 5줄과 기존 `/etc/gumseo/*.env` 및 소스의 `.env.local` 내 공급자 키 존재 여부만 출력한다. 비밀번호·키 원문·상점 ID·메일 주소는 출력하지 않는다. 파일은 읽기만 하고 shell source/eval을 사용하지 않는다. 다른 서비스에 키가 있다는 사실은 본 서비스에 연결됐거나 실제 키가 유효하다는 증거가 아니다.

### 사용자 서버 점검 결과와 운영 키 준비

2026-11-26 사용자 화면: 일반 web/worker는 각각1/20(기존 DB 읽기만 준비). private-reader.env에는 AI 키·토스 테스트 키가 있고 test.env에는 공급자 키가 없으며 toss-sandbox.env에는 테스트 키만 있다. 조회한 위치에서는 운영 토스 키와 Resend 키가 확인되지 않았다. 다른 위치에 저장됐는지나 키의 공급자 유효성을 단정하지 않는다.

`sudo python3 deploy/iwinv/prepare-sales-credentials.py`는 소유자의 대화형 SSH에서 운영 위젯 live_gck/live_gsk·MID와 선택적 Resend 키를 입력받는다. 화면에 값을 표시하지 않고 `/etc/gumseo/sales/credentials.env`에0600으로 보관한다. 새 하위 폴더는0700이며 symlink/공개 권한 파일을 거절한다. 기존 AI 키를 읽거나 복사하거나 바꾸지 않는다. 토스 테스트 키와 활성화 플래그는 저장하지 않는다. 기존 test.env/private-reader.env/toss-sandbox.env·실행 컨테이너·전환 DB는 변경하지 않는다. 외부 HTTP 요청도 없다. 메일 키가 없으면 Enter로 건너뛰고 결제 키만 먼저 보관할 수 있다. 이것만으로 판매가 활성화되지는 않는다.

키는 채팅으로 전달하지 않는다. 토스 개발자센터 운영 키 화면에서 현재 MID의 위젯용 키 조합을 확인한다. 운영 키가 표시되지 않거나 발급되지 않았다면 테스트 키로 대체하지 말고 퀵오픈 이용 상점/권한을 확인한다. 메일은 기존 Resend 계정의 인증된 발신 도메인을 사용한다.

### 2026-11-26 추가: 고객용 AI 재사용·풍성한 본문 준비

소유자가 기존 AI 키 재사용 및 `/etc/gumseo/sales/runtime.env` 비공개 저장을 승인했다. 비용은 고객이 만족할 만큼 풍성한 답변을 우선한다는 답변에 따라 건당 예약USD0.50·일USD5·누적USD30을 준비했다. 실제 사용량을 보장하는 요금제가 아니며 현재 원장은 예약액을 보수적으로 비용 계산에 반영한다. 이는 하루 최소10건·누적60건 예약 규모에 해당하므로 실제 판매 공개 전 예산 소진 시 신규 결제를 제한하는 조건과 운영자 예산 인수를 함께 확인해야 한다. 이 단계에서 provider mode는 disabled다.

`sudo python3 deploy/iwinv/prepare-sales-runtime.py --prepare`는 기존 test.env의 암호화/서명/환경 초기 인증 값을 보존하고, sales/credentials.env의 운영 토스·메일 설정과 private-reader.env의 기존 AI 키를 승인 경로에0600으로 새로 저장한다. 기존 파일을 덮어쓰지 않으며 기존 서비스·DB·프로세스·비공개 reader를 바꾸지 않는다. 세 공급자 모드는 비활성이며 실제 요청0회다. 기존 관리자 개인 설정은 원래 DB에 보존돼 있으며 향후 새 운영 DB의 관리자 설정 이전/분리를 별도로 검토한다.

운영 전용 rich-ko-v1은 한국어 장당800~1000자·쉬운 설명·구체적 사례를 요청하고700자 미만을 거절한다. 출력20000토큰/HTTP120초, 해당 AI 작업 lease180초다. 기존 standard9000/45초/60초와 고정 모델·가격표는 유지한다. 실패/시간초과 예약의 불확실 비용 보존·추가 호출 차단도 그대로다. 생성 요청은 모의 transport로 검증했으며 실제 완성본 품질 검수는 별도다.

compose.sales-candidate.yml은 별도 gumseo-sales 프로젝트/볼륨과 loopback3110을 사용하는 미설치 후보이며 기존3100 서비스를 건드리지 않는다. worker는 공급자 통신에 필요한 기본 bridge 네트워크를 사용한다. Caddy 판매 후보는3110을 바라보도록 맞췄다. 데이터/등록/관리자·배포·백업 연동과 공급자 준비가 끝나기 전 후보 파일만으로 외부 판매를 시작하지 않는다.

## 한 번에 실행하는 전환 (2026-11-26)

사용자가 반복 SSH 작업 대신 일괄 처리를 지시했다. `sudo python3 deploy/iwinv/sales-batch.py --activate`는 준비만 하는 이전 명령과 다르게, 모든 검사 통과 후 고객이 실제 결제할 수 있는 판매 경로를 활성화한다. 자동 시험 결제·환불·AI 생성·메일 발송은 하지 않으며, 전환 뒤 고객 요청에 따른 실제 공급자 호출은 활성화된다.

순서: 최신 실행 이미지 지문 대기 → 고정3개 설정 파일의 기존 root/gumseo 소유·일반 파일·단일 링크 확인과0600/root 권한 정리 → 승인된 runtime.env 생성/기존 설정 일치 검사 → 분리된 판매 볼륨 준비 → 기존 관리자 비밀번호 해시·방문 기록만 복사(모의 주문 제외, 기존 실제 운영 주문이 있으면 거절) → 결제·AI·메일 서명 등록과 재검증 → 판매 서비스 시작·정상 상태/암호화 백업 확인 → 프록시 전환과 고객 경로/모의OTP 차단 확인 → 활성 상태 기록. 기존 test/reader DB와 pay.gumseo.kr 경로는 보존한다.

새 서비스가 정상으로 확인되기 전 기존 도메인을 바꾸지 않는다. 실패 시 새 web/worker를 중지하고 준비 전 환경·프록시를 복원 시도한다. 새 DB/서명 파일은 지우지 않으며 재실행 시 정상 등록을 재검증한다. 실제 설정이 달라졌거나 파일이 unsafe하면 자동 덮어쓰지 않는다. 복원 자체 실패는 PROXY_ROLLBACK_REQUIRES_REVIEW로 명시한다. 성공 뒤 재실행은 상태 확인만 한다.

판매 활성화 후 자동 업데이트는 기존 모의 앱과 별도 판매 앱을 함께 갱신하며 백업은 실제 판매 DB를 대상으로 한다. 상태 감시와 터미널 비밀번호 변경 도구도 판매 컨테이너를 선택한다. AI 작업 종료 대기는150초로120초 HTTP 요청보다 길게 유지한다.

결제 창 제공·승인 전에 서명된 AI/메일 준비와 예산을 확인하고, 주문별 작성 슬롯을 원자적으로 확보한다. 동일 주문 재요청은 슬롯을 늘리지 않으며 AI 호출 예약 시 자신의 슬롯만 소비한다. 20분 넘은 미결제/미시도 슬롯은 반환한다. 승인 불확실 슬롯은 임의로 반환하지 않는다. 예산이 소진됐으면 PG 승인 요청 전에 결제를 막는다. AI 원장에 이미 예약된 동일 주문을 다시 생성하지 않는다. 보관 기간 종료 시 슬롯도 금융 주문과 함께 파기한다.

판매 모드 메인은 별도의 사전 렌더 HTML을 사용해 '실제 결제 없음' 오표시를 제거하고, 정책 화면에는 현재 AI/메일 전송과 서비스 정보를 표시한다. 기존 `?screen=privacy` 주소는 같은 도메인의 실제 개인정보 페이지로 연결한다. 유료 주문 동의 기록에는 판매 정책 버전과 AI/메일 처리 고지 동의를 함께 기록한다.

검증은 모의 PG/AI·메일, 임시 DB에서 서명 등록/재실행/변조 거절, 일괄 전환 성공·공개 경로 실패 시 복원, 예산 슬롯/자정 경계·소진 차단, 개인정보 파기, 기존 자동 배포·감시를 포함한다. 실제 상점 키 유효성·최초 실결제·실메일 수신·운명서 내용 검수는 서버 실행 후 별도 확인해야 하며 이 스크립트가 완료됐다는 사실만으로 전체 출시 인수를100%로 표시하지 않는다.
