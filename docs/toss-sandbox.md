# 토스 결제위젯 로컬 시험 환경

2026-11-15. 일반 사이트와 GitHub Pages에는 실제 결제 SDK/게이트웨이를 등록하지 않았다. 별도 loopback 서버에서 합성 주문만 시험한다. `.env.local`의 테스트 위젯 키는 비공개 저장 완료했고 형식을 확인했다. 실결제 활성화, 실제 고객정보 전송, 실제 이메일 발송, 운영 공개 배포는 수행하지 않는다.

## 실행

```sh
npm run toss:sandbox -- --test-network
```

서버는 `http://127.0.0.1:3211`에서만 수신한다. 이 주소는 서버가 실행된 컴퓨터 안에서만 열리며 모바일 공개 접속 주소가 아니다. 기존 앱의 CSP와 `APP_MODE=local`, `EXTERNAL_EFFECTS=disabled`를 유지한다. 명시적 CLI 플래그 없이는 시작하지 않는다. 플래그는 이 격리 시험 서버의 Toss 테스트 통신만 허용한다. 실판매 설정을 바꾸지 않는다.

- DB는 `var/toss-sandbox/journey.sqlite`로 강제 분리하며 기존 DB 환경변수를 덮어쓴다. private directory와 DB symlink를 거부한다.
- 가상 출생정보와 `toss-synthetic@example.invalid`만 내부에서 생성한다. 출생정보·이메일·전화번호 입력 인터페이스나 임의 주문 생성 API를 제공하지 않는다.
- 기존 가상 주문을 재사용한다. 재시작하거나 창을 닫았다고 신규 결제를 만들지 않는다. 완료/취소 주문을 임의 초기화하지 않는다.
- SDK는 버튼을 누른 뒤 공식 `https://js.tosspayments.com/v2/standard`에서 로드한다. 비회원 `ANONYMOUS`, KRW 22,000원, 고정 가상 상품명·주문 ID·로컬 반환 URL만 사용한다. 이름/출생일/이메일/전화번호를 결제 요청에 추가하지 않는다.
- 반환 URL은 결제키를 HTML에 반영하지 않으며 클라이언트가 먼저 history에서 쿼리를 지운다. 중복 파라미터·주문·금액을 확인한 뒤 동일 출처 POST로 승인한다. GET 성공 페이지나 공급자의 실패 메시지를 결제 증거로 취급하지 않는다.
- HttpOnly SameSite=Lax cookie와 정확한 Host·Origin 검증, JSON 본문 크기 제한, no-store/no-referrer, 외부 프레임 차단을 적용한다. Lax는 Toss에서 돌아오는 top-level GET을 지원하기 위한 선택이다.
- 결제수단·약관 렌더링 완료 후에만 결제 버튼을 허용한다. SDK 로딩 실패 후 재시도가 가능하고 결제 요청 동시 실행을 막는다.
- 서버 승인에는 별도 `TOSS_TEST_MID`가 필요하다. 없으면 SDK 렌더링만 가능하고 승인·조회·취소는 네트워크 호출 전에 차단한다. 키만으로 실제 사업자와 상점의 연결을 확정하지 않는다.
- 승인 확인 시 기존 TossOrderCoordinator가 주문 소유권·금액·결제키·MID·KRW·일회성 NORMAL 유형·상태·잔액·승인 시각을 검증한다. 응답 누락은 저장된 결제키 조회로 복구한다. 백그라운드 작업은 격리 DB에서 조회·규칙 기반 보고서·로컬 메일 발송함만 처리한다. OpenAI나 이메일 외부 전송기를 연결하지 않는다.
- 관리자 인증은 토스 스크립트가 없는 별도 `/admin` 문서에서 수행하며 외부 스크립트·통신을 CSP로 차단한다.
- 환불은 실제 관리자 비밀번호와 TOTP 인증, 최근 인증 정책을 통과해야 하며 고정 가상 주문의 전액 취소만 제공한다. 중요 작업 전 인증이 만료되면 다시 로그인한다. 취소 응답 누락도 조회로 복구한다.

## 검증

- 타입 검사 및 464개 단위/통합 테스트 통과. 위젯 승인 응답 누락 → 저장된 결제키 조회 → 유료 권한 복구 → 관리자 전액 취소를 실제 계약 파서·HTTP 어댑터·DB 코어에 가짜 fetch를 연결해 검증했다.
- `npm run test:toss-browser`: 모바일 Chromium, 모바일 WebKit, 데스크톱 Chromium에서 공급자 요청을 모두 가로채고 가짜 SDK를 사용한다. SDK 실패/재시도·약관 초기 선택/동의 해제/재동의/미동의 오류 후 재시도·비회원·서버 금액·성공 콜백·새로고침·변조/중복 파라미터 차단·실패·조회·관리자 취소를 검증한다. 실제 Toss 승인 완료의 증거가 아니다.
- 별도로 저장한 테스트 클라이언트 키로 실제 Toss SDK와 결제수단/약관 로딩을 모바일 크기 Chromium에서 확인했다. 결제수단 렌더링과 MID 미설정 시 결제 버튼 차단을 먼저 확인했다. 이후 운영자가 제공한 MID를 비공개 저장하고 테스트 카드사 인증 화면 진입 및 사용자 취소(USER_CANCEL)를 확인했다. 카드번호·휴대폰·간편결제 로그인 등 실제 개인정보는 입력하지 않았다. SDK가 추가하는 인라인 스타일과 공식 Toss 폼 전송을 시험 origin에만 허용하고, 실제 결제창 진입 시 CSP 위반이 없음을 확인했다. 취소 후 격리 DB는 pending 주문 1건, 유료 주문/승인 시도/PG 원장 0건이었다. 실제 카드 인증 완료·서버 승인·환불은 실행하지 않았다. 이 결과만으로 시크릿 키 유효성이나 가맹점 심사 완료를 주장하지 않는다.

WebKit이 별도 실행파일을 요구하는 개발 환경에서는 다음처럼 실행한다.

```sh
WEBKIT_EXECUTABLE=/workspace/work/run-webkit.sh PLAYWRIGHT_SKIP_VALIDATE_HOST_REQUIREMENTS=1 npm run test:toss-browser
```

## 남은 항목

운영자 제공 MID는 비공개 저장했으며, 인증 후 응답 MID와의 독립 대조는 남아 있다. 실제 테스트 인증→승인→조회→전액 취소, 실제 토스 장애/재전송 검증이 필요하다. 사업자/상품 심사, 결제 UI에서 제공할 결제수단, 허용 도메인 및 반환 URL 등록, 운영 TLS/DB/worker, 실제 기기 테스트는 별도다. 가상계좌·부분취소·복합 결제는 지원 완료로 표시하지 않는다. 보안 검토 후 일반 사이트의 실제 테스트 경로와 관리자 경로에 적용해야 하며, 이 격리 시험 화면은 상용 결제 페이지가 아니다.

공식 문서: https://docs.tosspayments.com/guides/v2/payment-widget/integration


## 다음 인증의 경계
공식 테스트 안내에 따르면 국내 카드에 공통으로 쓸 수 있는 테스트 카드번호는 제공되지 않으며, 카드사/간편결제의 인증에는 본인 결제수단이 필요할 수 있다. 임의 번호를 만들거나 실제 카드·인증 정보를 대화로 받지 않는다. 현재 개발 서버는 loopback 전용이라 운영자가 원격 접속할 수 없다. 접속 가능한 승인된 시험 환경을 준비한 뒤 운영자가 카드사/간편결제 화면에서 직접 인증해야 실제 승인·전액 취소 검증을 마칠 수 있다. 실제 유료 판매 활성화 승인은 별개다.

- https://docs.tosspayments.com/blog/how-to-test-toss-payments
- https://docs.tosspayments.com/guides/v2/get-started/environment

재시작 시 구매 이메일로 주문을 찾더라도 원 풀이의 세션 ID는 달라질 수 있다. 격리 서버는 주문 소유권을 먼저 검증한 후 해당 주문의 저장된 입력이 고정 가상 fixture인지 직접 대조한다. 원 풀이의 세션 소유권을 옮기거나 실제 고객 조회 규칙을 완화하지 않는다. 새 인증 세션으로 기존 주문을 검증하는 회귀 테스트를 추가했다.
