# 거래기록 보존 검토 도구 — 읽기 전용

**2026-11-21 후속:** worker의 보존·파기 및 외부 원장/복원 연결은 [거래 보존·자동 파기와 외부 삭제 원장](retention-runtime.md)에 구현·검증했다. 이 문서 아래는 읽기 전용 도구와 단계별 준비 당시 기록이다. 운영 자동 파기는 비활성이며 법무/호스트 인수는 남는다.

2026-11-21. 5.2.4의 준비 작업이며 자동 파기 구현 완료가 아니다. 실제 데이터 삭제·정책 승인·서버 설정 변경을 하지 않았다. 기존 worker의 콘텐츠 만료/세션 정리 동작을 변경하지 않는다.

`npm run retention:plan`은 인자 없으면 비활성 상태만 출력하고 DB를 열지 않는다. 검토자가 DB 경로와 소유자 전용 정책 파일을 명시한 경우에만 기존 SQLite를readOnly로 열어 일관된 조회 트랜잭션으로 집계한다. 생성/UPDATE/DELETE 명령이나 --apply 옵션은 없다. 런타임에도 dist/retention-plan.js를 포함하지만 자동 worker/타이머에 연결하지 않는다.

```bash
npm run retention:plan -- --db /private/path/existing.sqlite --policy /private/path/review-policy.json
# 설치 이미지에서 수동 실행 시 같은 인자를 사용
# node dist/retention-plan.js --db ... --policy ...
```

정책 JSON은 version=1,purpose="review-only",transactionYears(1~20 정수),reviewedAt(검토 시각ms),holdsReviewed=true,heldOrders(UUID 목록) 필드만 받는다. 파일은 소유자 전용 일반 파일·단일 링크여야 하며 심볼릭 링크와 공개 권한은 거절한다. 코드가 법정 보존 기간을 정하지 않는다. 예제 테스트의5년은 가상 정책일 뿐 실제 상품/기록별 법적 근거 승인이 아니다. 정책 파일을 Git/고객 화면에 게시하지 않는다.

미래/24시간 초과 검토 시각, 법적 보류 목록, 미종결 문의, 진행 중 생성 작업, 미확정 결제/환불 상태, 누락·역전·미래 결제 날짜는 검토 후보에서 제외한다. 기산점은 생성·승인·환불 완료 중 가장 늦은 시각이다. 달력상 연도를 더하며 윤일 경계는 이른 날짜로 앞당기지 않는다. 기준을 넘은 기록도 expired-review-candidate일 뿐 삭제 승인이 아니다. stdout은 건수와 사유별 집계만 출력하고 주문번호·연락처·출생정보·정책 내용은 출력하지 않는다.

## 남은 연결

실제 계약/결제/분쟁/기타 기록별 보존 근거와 기간을 검토해야 한다. 사람이 작성한 보류 목록은 외부 법적 보류 원장의 최신성/완전성을 증명하지 않는다. 실제 보류 등록·해제의 관리자 감사, 기록 유형별 분리, 진행 중 PG/메일/AI 작업과 의존 레코드 확인, 삭제 체크포인트/백업 복원 보호·외부 삭제 원장 대조, 파기 실행과 장애 복구까지 구현/검증하기 전 자동 파기를 활성화하지 않는다. 실제 운영에서는 부하를 고려해 검증된 읽기 전용 스냅샷에서 먼저 검토한다. 현재 도구는 모든 거래를 일괄 삭제하거나 기존 개인정보 삭제/콘텐츠 만료 정책을 대체하지 않는다.

검증: 보류/분쟁/작업/결제 미확인 제외, 정책 최신성, 기산점·경계, 누락 날짜·미완료 환불 차단을 단위 테스트했다. 가상 SQLite로 CLI 실행 후 DB 원본 bytes 불변·주문번호 미출력·공개 권한 정책 거절을 확인했다. 실제 고객 DB/정책/외부 서비스는 사용하지 않았다.


환불 예외 보강: 주문이paid 상태여도 미완료/오류/완료시각 미확인 환불이 있으면 unresolved-refund로 제외한다. 결제 상태와 환불 원장 건수가 맞지 않는 경우도 financial-review-required로 보류하며, 필수 카운터가 누락/음수/비정상이면 후보를 만들지 않는다. 가상DB의 오래된 결제에 오류 환불 행을 추가해도 만료 후보에서 제외되는 것을 CLI로 확인한다.


## 분리 보존 저장소의 파기 엔진 (기본 비활성)

`lib/retained-records.ts`는 기존 orders/문의/백업에 아직 연결하지 않은 별도 저장소 엔진이다. 명시적으로 초기화한 저장소에서 계약·결제·취소 묶음5년, 종결된 분쟁3년 기준으로 만료를 계산한다. 호출자는 이미 암호화한 최소 보존 payload를 전달해야 한다. 법적 보류·미종결 분쟁·미확인 처리·활성 작업은 파기하지 않는다. 재등록으로 보류가 풀리거나 기한이 짧아지지 않으며, 파기 영수증이 있는 ID의 재유입은 거절한다.

실행은 기본 disabled이며 명시적 실행과 복원 삭제 보호 확인 없이는 거부한다. 이 확인값 자체가 외부 원장의 최신성을 검증해 주지는 않는다. 실제 연결 시 별도 검증된 최신 원장 증거와 관리자 권한·감사가 필요하다. 최대100건을 원자적으로 지우며 영수증 기록/삭제 중 실패는 모두 롤백한다. 파기 영수증 보관 정책 역시 실제 운영 전 별도 확정한다.

가상 메모리DB에서 비활성·복원 보호 거부,5년/3년 경계, 보류·작업·미종결 제외, 보류 명시 해제, 재등록 기한 유지/삭제 항목 재유입 거부, SQL 실패 전체 롤백, 열린 분쟁 재등록 시 null 종결일 유지4개를 검증한다. 실제 주문/문의 저장소 이관·보류 등록 감사·worker 연결·외부 삭제 원장/백업 복원 보호가 남으므로5.2.4는 아직 완료가 아니다. 실제 고객 데이터 삭제/서버 정책 변경은 하지 않았다.


주문 연결 준비: order-retention-stage.ts는 명시적으로 호출한 경우에만 서로 다른 DB 사이에서 거래 필드·기존 암호화 연락처/동의 증거를 새 AES-GCM payload로 분리 저장한다. 출생정보/차트/운명서 본문은 조회하지 않는다. 최근 보류 검토·독립된 DB·단일 배치 트랜잭션을 요구하고 미확인 환불/진행 작업/분쟁 보류를 보존 상태로 전달한다. pending 미승인 주문은 원본에 남기고 이관하지 않는다. 원본 주문과 자식 기록은 삭제하지 않는다. 내부 페이지 커서는 주문ID이므로 외부 응답·로그에 게시하지 않는다.

현재는 worker/관리자 API에 연결하지 않았고 실제 데이터 이관은 수행하지 않았다. 실제 실행 전 원본/분리 저장소의 보류 등록·해제 동기화, 암호화 키/원본 출처·정책 버전 검증, 계약 증빙 필드 적정성, 원본/백업 삭제와 외부 원장 복원 보호 연결이 필요하다. 따라서 보존·파기 전체 항목의 완료율은 유지한다.
