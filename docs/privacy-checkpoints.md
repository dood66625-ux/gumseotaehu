# 삭제 이력 자동 저장과 복구 전 검증

이 기능은 로컬 복구 안전장치다. 최신 삭제 목록을 오프사이트에 보관하거나 개인정보·거래기록 보존기간을 확정하는 기능은 아니다. 실제 고객정보 외부 전송이나 보존기간에 따른 거래기록 자동 삭제를 활성화하지 않는다.

## 변경

작업자가 약 30초마다 현재 DB의 삭제 tombstone을 확인한다. 새 삭제가 있으면 서명된 불변 manifest와 `latest.json` 영수증을 생성한다. 삭제가 없으면 같은 manifest를 재사용하고 영수증만 약 5분마다 갱신한다. 파일은 0600, 폴더는 0700이며 임시 파일 fsync → 원자적 rename → 폴더 fsync로 공개한다. 동시 작업자는 SQLite write transaction으로 직렬화한다. 현재 manifest 상한은 16MiB/10만 건이다. manifest 변경 세대의 자동 파기는 하지 않는다.

- 기존 삭제 기록 형식(v1 signed manifest)은 유지한다.
- 별도 영수증에 원본 DB UUID, 생성 시각, manifest SHA-256/파일명/개수 및 HMAC 서명을 기록한다. 이름·이메일·출생정보·보고서 본문을 영수증에 넣지 않는다. 주문 UUID도 개인과 연결 가능한 식별자이므로 비공개로 취급한다.
- DB 경로와 데이터 키 세대별로 저장 폴더를 분리한다. 같은 폴더에서 다른 DB UUID를 발견하면 덮어쓰지 않는다. 새 DB로 초기화했다면 이전 체크포인트는 별도 보관하고 새 경로로 시작한다.
- 잘못된 서명·변조·symlink·과대 파일·다른 원본 DB·미래 시각·24시간보다 오래된 영수증을 복구 전 차단한다. 영수증에 맞는 manifest가 있어야 한다.
- 복구는 신규 오프라인 파일에만 수행한다. 원본 DB를 바꾸거나 서버를 시작하지 않는다. 삭제 적용 후 보고서/출생정보가 제거되고 생성 작업이 취소되지만 결제 사실은 보존된다. 기존 인증 폐기·메일 보류도 유지한다.
- 작업자는 저장 실패를 민감정보 없는 코드로 로그에 남긴다. 관리자 화면에는 체크포인트 생성 실패/10분 이상 오래됨/미생성을 경고한다. 메타데이터가 있는 실행 패키지의 worker health probe도 실패·기한 경과를 감지한다. Docker healthcheck는 경보 표시이며 자동 재시작을 보장하지 않는다.

## 명령

```sh
# 현재 DB의 로컬 체크포인트 생성/갱신. 결과는 경로/개수만 출력한다.
npm run privacy:checkpoint
# 선택적으로 별도의 NEW private directory 사용
npm run privacy:checkpoint -- var/privacy/manual-checkpoints
# 새 백업에는 원본 UUID가 포함되도록 체크포인트를 먼저 생성한다.
npm run backup
# backup/checkpoint 명령이 알려준 최신 latest.json 경로 사용
npm run restore -- var/backups/<archive>.gsb var/recovery/check.sqlite --checkpoint <private-directory>/latest.json
# 과거 데이터 키의 백업을 현재 키로 복구하는 기존 옵션 유지
npm run restore -- var/backups/<old>.gsb var/recovery/current.sqlite --checkpoint <current-private-directory>/latest.json --archive-key-file var/keys/old-data.key
```

현재 DATA_KEY로 체크포인트 서명을 확인하고, 백업의 암호화는 archive key로 해제한다. DB UUID가 같아야 한다. 키 교체 시 폴더를 분리하므로 과거 서명의 파일을 새 키로 덮어쓰지 않는다. 교체한 DB/키로 새 체크포인트를 생성하고, 복구에 필요한 과거 키와 삭제 이력도 안전하게 따로 보관한다.

구형 백업에는 원본 UUID가 없을 수 있다. 이 경우 `--checkpoint` 복구는 차단하며 최신 삭제 목록을 담당자가 독립 확인한 뒤 기존 `--deletions <signed manifest>` 경로로 복구할 수 있다. 이 수동 경로는 생성 시각/DB UUID를 자동 검증하지 않으며 새 백업의 기본 절차로 권장하지 않는다. 24시간 이상 장애로 최신 영수증을 만들 수 없는 경우도 담당자가 최신 삭제 이력을 별도로 확보·대조해야 한다. 날짜를 임의 변경하거나 서명을 다시 만들어 제한을 우회하지 않는다.

## 한계

**서명·24시간 이내라는 사실만으로 가장 최신인 파일임을 증명하지 못한다.** 같은 DB의 이전 영수증·manifest 전체가 함께 되돌아가면 외부 기준 없이는 이를 완전히 감지할 수 없다. 특히 24시간 안의 오래된 파일도 서명은 유효할 수 있다. 원본 서버 손실에 대비해 담당자는 최신본을 별도 안전한 저장소에 동기화하고 복구 시 그 최신본을 사용해야 한다. 실제 오프사이트 전송은 계정·보안 설정·권한·승인 후 별도 구현/검증이 필요하다. 이 작업은 외부 업로드를 하지 않았다.

삭제가 DB에 반영된 뒤 다음 작업자 주기 전에는 최대 약 30초의 로컬 체크포인트 지연이 있다. 복구 직전 원본이 살아 있으면 `privacy:checkpoint`로 다시 갱신한다. 원본과 외부 최신본 대조를 생략하지 않는다. 디스크 전체의 보안 소거, 법적 보류/거래기록 기한 파기, 오래된 manifest·백업의 매체 삭제는 이 기능의 범위 밖이다.

체크포인트 실패나 파일 위변조는 운영자 조사가 필요하다. 잘못된 파일을 조용히 덮어써 정상으로 표시하지 않는다. 저장매체/권한·파일 무결성과 올바른 DB·키를 확인한 후 안전한 새 경로에 재생성한다. 실제 운영에서는 로그 수집·외부 경보와 디스크 용량 모니터링을 추가해야 한다.

## 검증

가상 DB로 새 삭제 반영/불변 manifest 재사용/서명·시각·변조·symlink 차단/다른 DB 복구 차단/키·DB 경로별 폴더 분리를 시험한다. 삭제 전 백업 + 삭제 후 체크포인트로 복구해 보고서와 출생정보는 제거되고 paid 상태는 유지되는 것을 확인한다. 저장 실패·지연과 정상 갱신 후 상태 회복도 검증한다. 실제 고객 데이터나 외부 저장소는 사용하지 않는다.

2026-11-15 실행 결과: 타입 검사·479개 단위/통합 테스트·Next.js/worker 빌드 통과. 모바일 Chromium·모바일 WebKit·데스크톱 Chromium의 기존 구매/재열람/환불/관리자/접근통제 E2E 33개 통과. 실제 복구 CLI도 fresh checkpoint 성공과 오래된 checkpoint 차단을 검증했다. 체크포인트 메타데이터 테이블은 스키마 v9에 등록했으며, 원본 UUID는 최초 체크포인트에서 한 번 생성한다. 실제 고객정보·오프사이트 전송·실결제·실메일·운영 공개 없음.
